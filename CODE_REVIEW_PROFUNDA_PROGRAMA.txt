2. BUGS POTENCIAIS - LÓGICA INCORRETA
================================================================================

2.1. CRÍTICO: Lógica de stock negativo pode estar inconsistente
─────────────────────────────────────────────────────────────────────────────

PROBLEMA:
A função rebuildStock() (linhas 2578-2592) calcula stock por armazém:

  for(const mv of DB.movimentos){
    const e=_stk[mv.mat];if(!e)continue;
    const q=mv.qtd||0;
    if(mv.tipo==='entrada'){e[mv.arm]=(e[mv.arm]||0)+q;e.__t+=q;}
    else if(mv.tipo==='saida'){e[mv.arm]=(e[mv.arm]||0)-q;e.__t-=q;}
    else if(mv.tipo==='transferencia'){
      e[mv.arm]=(e[mv.arm]||0)-q;
      if(mv.armDst)e[mv.armDst]=(e[mv.armDst]||0)+q;
      else if(mv.obraDst)e.__t-=q;  // <-- POSSÍVEL BUG
    }
  }

PROBLEMA 1: e.__t (total) pode não corresponder à soma de armazéns
- Se transferência para outra obra (mv.obraDst), subtrai-se __t
- Mas e[mv.arm] já foi subtraído
- Se depois se soma armazém por armazém, pode não bater

PROBLEMA 2: Ordem dos movimentos importa
- Se houver transferência e depois a mesma saída for apagada, stock fica errado
- Não há verificação de integridade após apagar movimento

PROBLEMA 3: Armazém null em transferência inter-obra não é tratado
- if(mv.armDst)e[mv.armDst]=(e[mv.armDst]||0)+q;
- Se armDst não existir, simplesmente não incrementa nada
- Poderia criar armazém implícito indesejado

SEVERIDADE: CRÍTICA
IMPACTO: Discrepâncias de stock, especialmente com transferências inter-obra

TESTE:
  1. Criar 10 un de material em armazém A
  2. Transferir 5 para armazém B (inter-obra)
  3. Verificar se A tem 5 e B tem 5
  4. Apagar a transferência
  5. Verificar se A volta a 10 e B para 0
  6. Comparar __t com soma de armazéns

3. PERFORMANCE - OTIMIZAÇÕES CRÍTICAS
================================================================================

3.1. CRÍTICO: Ficheiro HTML de 3.4 MB
─────────────────────────────────────────────────────────────────────────────

PROBLEMA:
- 7.656 linhas em single file
- SEED_DATA embebido (provavelmente 2-3 MB de JSON)
- Carrega tudo na memória no primeiro load
- Sem lazy loading de dados

SEVERIDADE: CRÍTICA
IMPACTO: Carregamento lento na primeira vez (especialmente mobile), alto uso de RAM

MÉTRICAS ESTIMADAS:
  - Download: ~1.5-2 MB (comprimido gzip)
  - Parse HTML: ~500ms (browser)
  - JSON.parse(SEED_DATA): ~200ms
  - rebuildStock() na inicialização: ~100ms
  - Total first load: ~800ms-1.5s

CORREÇÃO:
  1. Separar SEED_DATA em ficheiro JSON externo
  2. Implementar IndexedDB para dados históricos
  3. Lazy load tabelas grandes (só mostrar 100 linhas, carregar mais ao scroll)
  4. Minify e compactar melhor (estou vendo muito CSS e HTML redundante)

─────────────────────────────────────────────────────────────────────────────

3.2. ALTO: Cálculo de stock é O(n²) ou pior
─────────────────────────────────────────────────────────────────────────────

PROBLEMA:
rebuildStock() é chamado:
  - Na inicialização
  - Após qualquer movimento
  - Antes de qualquer cálculo de stock

Com 1.937 materiais e 2.243 movimentos, cada chamada é:
  O(materiais) + O(movimentos) = O(1937 + 2243) = rápido

MAS: Se houver nested loops em operações de UI:
  - renderStock() → map → stockMaterial() → rebuild se null
  - renderMovimentos() → map → linhaMovimento() → matById() + stockMaterial()

Isso pode ser O(n*m) onde n=movimentos, m=materiais.

SEVERIDADE: ALTO
IMPACTO: Tabelas com 100+ linhas renderizam lentamente

─────────────────────────────────────────────────────────────────────────────

3.3. ALTO: innerHTML reconstruído a cada refresh
─────────────────────────────────────────────────────────────────────────────

PROBLEMA:
Cada refrescar da view reconstrói a tabela inteira como string:
  t.innerHTML='<tr>...' + linhas.map(mv=>linhaMovimento(mv,true)).join('');

Isto é ineficiente para tabelas com 100+ linhas:
  - Serializar para string: O(n)
  - Parse HTML: O(n)
  - DOM reflow: O(n)

SEVERIDADE: ALTO
IMPACTO: Scroll lento, responsividade reduzida

CORREÇÃO: Usar DocumentFragment ou biblioteca como React/Preact

─────────────────────────────────────────────────────────────────────────────

- Rejeita 0

Se utilizador deixa campo vazio, parseFloat retorna NaN.
